## Goal
The desktop app tells you when a newer rdm is out and installs it with one
click, without losing a download in progress.

## Context / rationale
rdm ships prebuilt releases (see
[[milestone-06-releases-install]]), but the desktop app doesn't know about
them: to update, you download the new installer from the Releases page and
run it over the old one ([docs/install.md](../docs/install.md), Updating).
The updater was drafted into M6 and cut to the backlog so the first releases
could ship; this milestone builds it on today's code.

**What exists today** (checked against the code after v0.2.0):
- **Release pipeline.** One tag push runs `.github/workflows/release.yml`
  (generated by dist, hand-edited, `allow-dirty = ["ci"]`). Its GUI part is
  `release-gui.yml`, a dist `local-artifacts-jobs` job: tauri-action only
  **builds** there (Windows `nsis,msi`, macOS `app,dmg` for arm64 and x64,
  Linux `deb,appimage` on `ubuntu-22.04`), and a step collects only the
  installers into `artifacts-gui-*` workflow artifacts. dist's `host` job
  then creates the GitHub Release with every asset in one
  `gh release create`, marked pre-release for a tag like `v0.3.0-rc.1`.
  `release-checks.yml` (`post-announce-jobs`) checks the published assets.
  No `.rpm` is built (it rejects pre-release versions).
- **No updater at all.** `gui/src-tauri` has no `tauri-plugin-updater`,
  `tauri.conf.json` has `"plugins": {}`, and
  no `latest.json` is produced. tauri-action's own `latest.json` upload
  doesn't apply, because it doesn't create the release here.
- **Signing key.** The repo's Actions secrets hold only
  `HOMEBREW_TAP_TOKEN`; there is no `TAURI_SIGNING_PRIVATE_KEY` or
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and no public key is in the repo
  (see Owner setup).
- **GUI.** The Console layout's toolbar has a **Settings** popover
  (`components/settings/SettingsMenu.tsx`) with a Display section (kept in
  `localStorage`) and the engine-backed Downloads section. Finish
  notifications and toasts live in `components/feedback/`.
- **Quitting keeps downloads.** On `RunEvent::Exit` the GUI calls
  `Manager::shutdown`, which stops running downloads and saves them as
  **Paused** with their partial files; on the next start `Manager::load`
  restores them paused (no surprise network activity on launch).
- **Webview permissions.** `capabilities/default.json` grants only
  `core:default`; plugins (folder picker, open/reveal) are called from Rust
  commands, and the CSP's `connect-src` allows only IPC.
- **CLI.** dist's `install-updater = false`; the CLI updates with
  `brew upgrade rdm` or by re-running the installer one-liner.

**v0.2.0 and earlier have no updater**, so nobody on them is offered an
update in-app. The first release with the updater (v0.3.0 or its first rc)
is the base people update **from**; they reinstall by hand once to get it.

The engine/frontend split holds: the updater is the GUI's process setup
(the GUI crate in Rust plus its notice), not engine work. The engine gains
only what "pause for the restart and pick up exactly those after it" needs.

Roadmap: [roadmap.md](../roadmap.md).

## Scope
**In:**
- **The official Tauri updater plugin** (`tauri-plugin-updater`, v2) in the
  GUI crate. `tauri.conf.json` gets `plugins.updater.pubkey` (the update
  public key) and one HTTPS endpoint:
  `https://github.com/SimonPerryman/rust-download-manager/releases/latest/download/latest.json`.
  GitHub's `releases/latest` never points at a pre-release.
- **Rust-side only.** The check and the install run in rdm's own Tauri
  commands, as the folder picker does. The webview gets no `updater:*`
  permission and the CSP is unchanged.
- **Signed releases, signed apart from the build.** The GUI build job
  builds the updatable bundles unsigned; a separate `sign-gui-updates` job
  in `release.yml` signs them with `tauri signer sign --app-version` (the
  version goes into the signature) using `TAURI_SIGNING_PRIVATE_KEY` and
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. That job runs no build and no
  dependency install scripts, so the key never reaches code a compromised
  dependency could run. (Instead of `bundle.createUpdaterArtifacts`, which
  signs inside the build.) The bundles:
  - Windows: the NSIS `-setup.exe` and the `.msi`;
  - macOS: the `.app` as an `.app.tar.gz` per architecture, named like the
    `.dmg` so arm64 and x64 don't collide;
  - Linux: the AppImage.
- **A signed `latest.json` on every release**, written by the same job
  (tauri-action can't, see Context): the tag's version, a link to the
  release notes, `pub_date`, and one entry per installer kind, keyed
  `{os}-{arch}-{installer}` (`windows-x86_64-nsis`, `windows-x86_64-msi`,
  `darwin-aarch64-app`, `darwin-x86_64-app`, `linux-x86_64-appimage`), each
  with its asset URL on the tagged release and its signature. The app asks
  for its own installer kind's key, so an `.msi` install is never replaced
  by the NSIS setup, and a `.deb` reads the AppImage entry only to learn the
  version.
- **A release-time signature check:** before the release is created, the
  job verifies every signature (and its signed version) against the public
  key in `tauri.conf.json`, with a minisign check on Node's built-in crypto
  (`gui/scripts/updater-manifest.mjs`, no third-party code), and fails the
  release if any doesn't verify, an entry is missing, or the key is still
  the placeholder. `release-checks.yml` also requires `latest.json` and the
  macOS archives.
- **Signed versions are required** (`requireSignedVersion`): a tampered
  `latest.json` can't pair a newer version number with an older, genuinely
  signed bundle.
- **When rdm checks:** on start, then once a day while it stays open,
  while automatic checks are on; plus a **Check for updates** button in
  Settings that always works. A failed automatic check is logged, not shown;
  a failed manual check says so.
- **Asked once, not on by default:** the first time the app starts with the
  updater, a one-time prompt asks "Check for updates automatically?" (Yes /
  No), as a small card at the bottom left. No network check happens before it's answered. The answer is saved
  and changeable in Settings ("Check for updates automatically"), next to
  Check for updates and the current version.
- **The "Update available" notice:** the new version with a "What's new"
  link to its release notes beside it, two ways to install (below), and
  **Later**, which hides it until the next check (next start or next day).
  It's a slim bar under the toolbar: Restart now is always the primary
  button, Install when I quit the quieter one, and Later a text link. A
  failed download or a bad signature leaves the app as it was and says so.
  The owner approved the mock-ups on 2026-11-10.
- **Two ways to install, and running downloads are never lost:**
  - **Restart now:** downloads the update (with progress), then restarts
    into it. Downloads pause the way a normal quit pauses them (partial
    file and state saved) and nothing resumes on its own. If anything is
    downloading, the notice says so first ("Downloads will pause; you can
    resume them after the restart"). After the restart a one-line notice
    says how many downloads the update paused, with **Resume all** (exactly
    those) and a dismiss. On Windows the installer closes the app, so the
    pause runs before that (the plugin's before-exit hook).
  - **Install when I quit:** downloads and verifies the update now, without
    interrupting anything, and installs it at the next normal quit; the
    next start is the new version. Downloads running at that quit come back
    paused, as after any quit. Where a platform or format can't do this
    with the plugin, the owner decides the fallback before it's built.
- **Pre-releases are never offered to stable users.** The stable endpoint
  already skips them (`releases/latest`); on top of that, a stable build
  refuses an update whose version is a pre-release (a custom version check),
  so a mistaken `latest.json` can't move stable users onto an rc. **An rc
  build is offered the newest release including newer rcs** (rc.1 → rc.2 →
  the final release): it looks up the newest release's `latest.json`
  through GitHub's releases list instead of `releases/latest`.
- **Linux formats:** AppImage updates in-app. A `.deb` install gets the same
  notice with **Download**, which opens the release page, instead of the
  install buttons. No `.rpm` is shipped.
- **A test seam:** in debug builds only, environment variables point the
  updater at another endpoint and public key, and can stop Install at the
  point it would run the installer and restart. Tests and e2e use a local
  fixture serving a `latest.json` signed with a throwaway test key, never
  GitHub. A release build ignores them (compiled out, and asserted).
- **Docs:** `docs/gui.md` (the prompt, the notice, the Settings items),
  `docs/install.md` Updating (in-app for the desktop app; `.deb` installs
  download the new `.deb`; the one-time manual step from 0.2.0 and earlier),
  `CONTRIBUTING.md` (the signing secrets a release needs, and keeping the
  private key backed up), README highlights, CHANGELOG.

**Out (deferred):**
- **A CLI self-updater.** The CLI stays on `brew upgrade` or re-running its
  installer one-liner (dist's `install-updater` stays `false`): a second
  download-and-replace path to maintain and secure, for what one command
  already does.
- **Code signing and notarisation** (backlog). The updater's signatures are
  separate and free; they prove a bundle came from this repo's release, not
  who the publisher is to the OS.
- **Update channels as a user setting** (e.g. "include pre-releases"): not
  now.
- **Skip this version** and **in-app `.deb` updates** (backlog).
- **Delta updates, background installs without a restart, rollback.**
- **Linux `.rpm`** (not shipped) and the updater for other package managers
  (Homebrew cask, winget).

## Owner setup (before the first release with the updater)
1. Find the update keypair made during M6 (generated with
   `pnpm tauri signer generate`, with a password, and backed up). If it's
   lost, generate a new one in `gui/` with
   `pnpm tauri signer generate -w <path outside the repo>`; nothing uses the
   old one yet.
2. Add the private key and its password to this repo's Actions secrets as
   `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
3. Hand the **public** key (the `.pub` file's contents, safe to publish) to
   the PR that adds it to `tauri.conf.json`.
4. Keep the private key and password backed up outside GitHub. Losing
   either means installed copies can never update in-app again; users would
   reinstall by hand. Once these secrets exist, a release build without them
   fails rather than shipping unsigned updates.

## Open questions
All answered by the owner on 2026-11-10:
1. **When to check:** on start, then once a day while the app stays open,
   plus a Check for updates button in Settings.
2. **Automatic checks:** not on by default. A one-time first-run prompt
   asks; nothing is checked before it's answered, and the answer can be
   changed in Settings.
3. **Later:** hides the notice until the next check. Skip this version goes
   to the backlog.
4. **Running downloads:** the notice offers **Restart now** and **Install
   when I quit** (applied at the next normal quit, no interruption).
   Nothing is lost. If Install when I quit isn't possible somewhere, the
   owner picks the fallback (it isn't needed: every in-place format can).
   Revised by the owner at the mock-up review: Restart now pauses downloads
   like a normal quit, nothing resumes on its own, and after the restart a
   bar offers Resume all for exactly the downloads the update paused. This
   replaces the first answer, where those downloads continued on their own.
5. **Linux `.deb`:** the notice offers Download (the release page) instead
   of installing; in-app `.deb` updates go to the backlog. AppImage updates
   in-app.
6. **rc builds:** offered newer rcs and the final release; stable builds see
   only stable releases.
