# Contributing

How to build and test rdm from source. Conventions for contributors and coding
agents live in [AGENTS.md](AGENTS.md).

## Layout

The repository is a Cargo workspace: the `rdm` engine library and CLI at the
root, and the GUI's Rust crate (`rdm-gui`) under `gui/src-tauri`. All download
logic lives in the engine; the CLI and the GUI are thin frontends over it.

## Building the CLI

You need [Rust](https://www.rust-lang.org/tools/install) (stable; the MSVC
toolchain on Windows, which needs the Visual Studio C++ Build Tools).

`cargo install --locked --git https://github.com/SimonPerryman/rust-download-manager rdm`
builds the `rdm` binary and puts it in `~/.cargo/bin`. The trailing `rdm`
picks the CLI package out of the repository's workspace. From a clone,
`cargo install --locked --path .` does the same.

## Building the desktop GUI

The GUI lives in [`gui/`](gui/). You need:

- Rust (as above);
- [Node.js](https://nodejs.org/) and [pnpm](https://pnpm.io/);
- the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for your
  OS. On Windows that's the Visual Studio C++ Build Tools and the WebView2
  runtime, which ships with Windows 11.

```sh
git clone https://github.com/SimonPerryman/rust-download-manager.git
cd rust-download-manager/gui
pnpm install
pnpm tauri build    # release build; the app and installers land in ../target/release/
```

On Windows, run the build from a Developer PowerShell for VS so the MSVC
linker is on `PATH`.

To start the GUI, run the app that `pnpm tauri build` produced, or
`pnpm tauri dev` from `gui/` during development.

## Testing

```sh
cargo build                  # the engine and CLI
cargo test                   # fast, offline test suite
cargo test -- --ignored      # also run the live network smoke tests
cargo clippy -- -D warnings  # lint
cargo fmt --all --check      # format check

cd gui
pnpm test                    # frontend unit tests
pnpm lint                    # frontend lint
```

The default tests run offline against a local HTTP server. CI builds, lints and
tests on Linux and Windows; macOS isn't tested yet. Format checks (rustfmt,
oxfmt) and the frontend lint don't depend on the OS, so CI runs them on Linux
only.

The GUI also has an end-to-end suite that drives the real app with
WebdriverIO; see the [`gui/e2e` package](gui/e2e/package.json) (`pnpm e2e`),
which needs `tauri-driver` and, on Windows, Microsoft Edge WebDriver.
`pnpm screenshots` in the same package regenerates the images in
[`docs/screenshots`](docs/screenshots/) used by the README and docs.
Each run picks free ports for `tauri-driver`, so parallel runs (e.g. in
separate worktrees) are safe; set `RDM_E2E_DRIVER_PORT` /
`RDM_E2E_NATIVE_PORT` to pin them.

## Cutting a release

The CLI and the desktop app share one version, set in `Cargo.toml`'s
`[workspace.package]`, and one tag releases both.

1. **Bump PR.** Set the new version in `Cargo.toml` (`[workspace.package]
   version`) and `gui/package.json`, run `cargo update -w` so `Cargo.lock`
   follows, and in `CHANGELOG.md` rename `## Unreleased` to
   `## X.Y.Z - YYYY-MM-DD` (and start a new, empty `## Unreleased` above it).
   The changelog section becomes the release notes, so write it for users.
   `node gui/scripts/check-release-version.mjs vX.Y.Z` checks that everything
   agrees.
2. **Tag the merged commit** on `main` and push the tag:

   ```sh
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

The tag starts the Release workflow (`.github/workflows/release.yml`): it
checks the versions again, builds the CLI archives and installers with
[dist](https://github.com/axodotdev/cargo-dist) and the desktop bundles with
`tauri-action`, publishes them as one GitHub Release, pushes the Homebrew
formula to `SimonPerryman/homebrew-tap` (stable tags only; this needs the
`HOMEBREW_TAP_TOKEN` secret), then smoke-tests each CLI archive and checks
every expected asset is attached. A stable tag also installs the CLI with each
one-liner.

A pre-release tag such as `vX.Y.Z-rc.1` needs the same versions
(`X.Y.Z-rc.1`) but may keep `## Unreleased` as its notes. It's published as a
pre-release, which `releases/latest` and Homebrew skip.

`release.yml` was generated by dist and then hand-edited to this repo's CI
rules, so `dist generate` leaves it alone (`allow-dirty` in
`dist-workspace.toml`). When bumping dist, regenerate it and re-apply the
edits listed at its top; `pnpm lint` (in `gui/`) checks the pins, the trigger
and the permissions.

The repository allows only GitHub's own actions and a short list of
third-party ones (Settings, Actions, General: "Allow specified actions").
A workflow that uses any other third-party action fails at startup, before a
job runs. Pull-request CI doesn't run the release workflows, so it won't
catch this: have a new action's `owner/repo@*` pattern added there before
the change that uses it is merged.
